# 办公室 Yeelight 接入与 Astra 交接

更新：2026-11-19。适用于已经安装、配置并在线的 Yeelight Pro 网关。目标是在另一台与网关同 LAN 的电脑上复用接入程序，先完成只读现场验证，再推进单灯受控操作和模型影子评估。

这是一份交接说明，不代表办公室已经验收。接收端先读本文件、[AGENTS.md](../AGENTS.md)、[README.md](../README.md)、[验收边界](acceptance.md)，再读与当前步骤有关的代码。完整聊天记录不是运行依赖。

### 模型是否准备好了

已经有训练好的研究检查点，值得开始收集真实环境证据和准备影子评估；**尚未准备好无人值守控制**。影子评估指模型只给建议，由人核对，不接自动写设备链路。现场输入适配和评分调用还需要连接，当前并没有即插即用的办公室模型服务。

- 第 27 轮新增覆盖组的新合成题为 **528/528** 个状态在四种候选顺序下全对；包含历史题及新增训练回测的汇总为 **3129/3130** 个状态、**12135/12136** 次呈现正确。这不是独立真实家庭测试集。
- 仍有一个“灯已关、请求关灯”状态在特定顺序下错误建议再次关灯，而且置信度超过 99%。模拟执行层拦下了无须执行的动作，模型错误仍保留。
- 第 28 轮不训练，只做固定检查点诊断。第 27 轮模型在 32 个新状态、每状态 16 种顺序下，31/32 个状态全对（511/512 次呈现）；有一次应该开灯却选择保持。原来的错误在原顺序下仍能复现。
- 第 27 轮原流程因 swap 保护中止，后续独立 D2 流程补全诊断，原失败不改写。质量门槛也没有全过；**第 21 轮仍是保留的研究候选**，不是生产模型。不能把最新检查点默认升级为部署版本。
- 当前研究是八类灯光相关候选：开灯、关灯、阅读预设、保持、人工回退、刷新状态、不支持、澄清。它不是已覆盖全部窗帘、空调、场景联动的通用家庭控制器。
- 下一项训练对照拟保持 208 条训练记录、2,496 步及各候选位置曝光次数，只改变部分候选排列共享方式；目前仅 CPU 设计核对通过，尚未启动该轮训练。

完整证据：[repo 追踪页](home-training-tracker.html)、[同一 ShareOne 追踪页](https://s.shareone.vip/s/home-training-tracker)。权重、训练数据、逐条输出、运行回执均在原训练机/外部运行目录，不在 Git；克隆仓库不会下载模型。框架为 ms-swift 监督决策训练，不称为 Microsoft Decision-1 完整复现或已经完成 RLCD。

### 当前模型输入与输出

输入由家庭配置、目标灯状态、传感器数据、用户请求或触发原因、明确决策规则和八个候选组成。训练评分器将完整嵌套状态序列化成文本，通过 `messages` 传入，另提供 `kinds=[choice]`、`questions` 和 `options`；正确标签不进入推理输入。第 27 轮表示还附加照度/区间端点相对阈值的三项数值比较事实，不提供正确动作。

模型一次前向输出与候选顺序对应的 `probs` 数组。评分器先按原始 argmax 记录所选候选，不能把执行层拦截后的结果反算成模型答对。动作 ID 和具体设备参数由程序把候选与已核实的家庭配置对应起来；模型不直接生成自由格式的设备 API 命令，也不输出一段自然语言推理。向用户解释结果时，区分模型的概率输出和 Astra 根据输入作出的说明。

现场的 `profile.private.json` 目前仍不是可直接喂给研究评分器的完整输入：用户偏好、范围、规则、新鲜度和手动覆盖等必须核实或保持未知。八类合成输入合同不代表所有现实未知情况已有模型验收。原始概率尚未校准，不能将其当作正确率或权限。

## 2. 交接什么，以及如何分工

**唯一交接入口是本文件。** 所需的局域网源码、轻量启动脚本及依赖锁文件随本文件一起提交到仓库；另一台电脑克隆仓库后，在目录内新开 Astra 会话即可。不需要另取 ZIP 或完整 session。之前的 ZIP 是发布前的临时快照，不再作为正式交接版本。

原会话继续训练研究，办公室会话负责设备接入与现场证据；不要同时改同一训练目录或刷新同一 ShareOne 页面。

完整 session 仅在追查某个历史决定时作为私有参考。它包含旧路径、已被替代的尝试及可能的私人信息；复制聊天记录也不会复制代码、依赖、权重、网络连接或登录状态。官方 `codex resume` 说明的是恢复已保存的聊天，不能把它当作跨电脑部署包：[Codex CLI 文档](https://learn.chatgpt.com/docs/codex/cli)。本次不导出或提交完整 session，也不复制 `.codex` 登录信息或 SSH 私钥。

### 获取代码

首次使用，在准备存放项目的目录执行：

```bash
git clone https://github.com/sudoprivacy/local-decision-models.git
cd local-decision-models
git rev-parse HEAD
```

已有 checkout 时，先检查 `git status --short` 和当前分支；在干净的 `main` 上用 `git pull --ff-only` 更新。存在本地改动时保留改动，另建 checkout 或先正常协调，不做强制 reset。现场回执记录实际提交号。以下文件应随提交齐全：

- `scripts/home_lan.py`、`scripts/home_lan.py.lock`
- `src/ldm/yeelight.py`、`yeelight_discovery.py`、`home_connect.py`、`home_profile.py`
- 同目录 `__init__.py`、`contracts.py`、`data.py`、`home.py`、`home_mock.py`

## 3. 办公室先准备这几件事

1. 网关已入网、在线；由有权操作该环境的人在易来 App 中一次性开启“局域网控制 → 第三方控制”。本程序不能自动开此开关。开好后，这条局域网读取路线不再需要登录易来、MCP 授权扫码或云端凭据。
2. 电脑与网关在可互通的局域网内。相同 Wi-Fi 名字不保证同一广播域；检查访客网络、AP/客户端隔离和 VLAN。支持的自动发现范围是已连接的 RFC1918 私有 IPv4 网段。
3. 在办公室电脑上运行 Astra 和连接脚本。电脑只承担局域网连接时，无须 DGX、CUDA 或 9B 模型；模型迁移/远程评分是另一个步骤。若由原电脑远程操作，另建已授权的远程访问通道，不能假定两地 LAN 自动互通。
4. macOS 若提示本地网络访问，允许实际运行脚本的终端/应用；按具体网络诊断防火墙，不通过关闭全局防火墙排障。发现使用 UDP 1982；只读查询使用 TCP 65443。
5. 接入测试期间让电脑保持唤醒。长期运行、防休眠、重启恢复及服务托管在现场验证后再安排；这份脚本是单次执行，不是常驻服务。

## 4. Mac 上的最短执行路径

下面命令在**克隆的仓库根目录**执行。不要照搬原 Windows 的盘符或原家庭的 IP。办公室接入使用本节的 `home_lan.py` 入口，不需要先安装完整训练环境或依赖其他工作区未提交的 CLI 改动。

### A. 安装轻量运行依赖并自检

已有 `uv` 可直接使用；否则依据 [uv 安装说明](https://docs.astral.sh/uv/getting-started/installation/)安装。已有 Homebrew 的 Mac 可执行 `brew install uv`。脚本声明 Python 3.13、pydantic、psutil，锁文件固定解析结果；首次运行需要下载缺少的解释器/包。

```bash
uv --version
uv run --locked --no-project --script scripts/home_lan.py self-test
```

成功返回 `status=passed`、`scope=synthetic_loopback_only`、`write_rejected=true`、`training_stack_imported=false`、`physical_commands_sent=0`。它只启动本机模拟网关，读取五类数据并确认写入被拒绝，不广播办公室网络，也不操作真灯。

不要为此先运行整仓库 `uv sync` 或下载训练权重。此脚本利用 [uv 的独立脚本依赖环境](https://docs.astral.sh/uv/guides/scripts/)，复用同一套局域网代码，不加载 PyTorch、Transformers 或 PEFT。首次安装完成后，`--offline` 可以限制 uv 后续不访问包源；这与脚本对局域网网关的访问是两回事。

### B. 自动发现并只读连接

```bash
uv run --locked --no-project --script scripts/home_lan.py connect \
  --root "$HOME/local-decision-models-runtime/office-yeelight"
```

新办公室使用新的外部运行目录。不要复制原家庭的 `gateways.private.json`、IP 或身份映射来初始化。运行目录必须位于源码目录外。

期待顶层 `status=read_only_connected`，`gateways_discovered` 与 `gateways_connected` 符合现场数量，`physical_commands_sent=0`。再检查每个网关的 `configuration.status`；连接成功不保证所有状态字段都能归一化。发现多个中枢会分别保存，不能直接合并成同一个家庭。

退出码：`0` 为全部只读连通；`2` 为未发现、发现不完整、部分连通或本地 API 不可用；`1` 为结构化配置/存储等错误。查看具体 `status/error_code`，不要把所有非零结果都解释成“第三方控制没开”。

多网卡时可选**这台电脑的局域网 IPv4**，不是网关 IP：

```bash
uv run --locked --no-project --script scripts/home_lan.py connect \
  --root "$HOME/local-decision-models-runtime/office-yeelight" \
  --interface <本机局域网IPv4>
```

已从现场网络信息确认网关 IP 时，可单独检查 TCP 清单，判断是否只有广播受阻：

```bash
uv run --locked --no-project --script scripts/home_lan.py inspect --host <网关IPv4>
```

`inspect` 只输出四类清单数量，不产生完整连接档案，不能代替自动发现及五类查询的验收。上面的尖括号是占位符，替换成实际地址后再执行。

### C. 数据留在哪里

运行目录中的 `home-connection-receipt.json` 是摘要；`gateways.private.json`、`gateways/<连接ID>/inventory.private.json` 和 `profile.private.json` 是私有连接、设备及配置记录。真实名字、地址、标识和逐条状态留在现场受控目录，不提交 Git，也不上传 ShareOne。

这里只取得顺序读取的快照，不是原子快照。接收时间不是设备事件发生时间；`state_fresh` 仍为未知，不能默认设成 `true`。开关电源不等于设备在线，最近没有移动不等于无人；灯组/情景名称不等于完整动作或成员定义。

## 5. 常见结果如何处理

| 结果 | 下一步 |
|---|---|
| `incomplete_lan_handoff_source` | 代码包缺文件；核对快照清单，不用猜测的替代实现继续 |
| `gateway_no_active_lan_interface` | 核对电脑地址、掩码、网卡在线及私有 IPv4；必要时指定本机网卡地址 |
| `no_gateway_discovered` / `discovery_incomplete` | 核对同 LAN、广播、权限、隔离、网关在线；已知 IP 时用 `inspect` 区分 UDP 和 TCP 问题 |
| `local_access_unavailable` / `local_api_unavailable` | 分别检查第三方控制、TCP 65443 可达性和固件；不反复走旧的扫码/SMS 登录路线 |
| `partially_connected` / `identity_conflict` | 按网关逐一核对；不要凭重复身份或模糊名字选一个去控制 |
| `configuration.status=unavailable` | 原始读取可能成功但格式映射失败；保留私有回执，按协议补适配，不捏造缺失字段 |
| 清单为空 | 与现场实际安装对照；连通不等于网关下有可操作设备 |
| `gateway_connection_profile_busy` | 检查同一目录是否还有连接进程；确认没有之后再处理遗留锁，不启动并行写同一档案的任务 |

之前同一台测试网关关闭第三方控制后，UDP 仍能发现、65442 加密通道仍响应、65443 读取失败；重新开启后恢复。**65442 能连接不代表已经取得加密凭据或可以直接使用加密控制。**

完整自动化规则、情景动作和灯组成员信息的 LAN 覆盖不完整。缺失保留 `null/unknown`。厂商说明及已查官方接口指向经账号授权的云端查询，实际账号响应和工具映射仍待验证；不要因此宣称日常灯光控制必须走官方 MCP，也不要宣称免云端已经导出全部配置。详见 [能力证据](yeelight-capabilities.json)。

## 6. 从只读到控制，再到模型

按以下顺序推进，可与原训练会话并行：

1. **只读现场验收。** 保存代码快照身份、操作系统、机型/固件、发现情况、五类查询数量、映射覆盖及未知项。私人标识不放公开报告。
2. **单灯受控操作。** 现场确定一盏普通灯、准确目标、允许动作及初始状态；接收端根据协议实现并测试独立写入适配器。目前没有可直接运行的真实 `set` 命令。先完成具体可审阅的目标/参数和回退方案，在当前用户授权范围内取得所需的动作确认，再执行一次、读回并观察实体效果，最后恢复约定状态。不要通过放宽 `YeelightReader` 白名单、把 mock 的地址改成真实 IP，或把训练分数当作授权来接通写入。
3. **状态链路。** 验证实际设备的电源/在线含义、报告时间、状态刷新、手动变化和已有自动化冲突。多房间、群组或情景操作等到范围和成员确定后再做。
4. **模型影子评估。** 对真实任务记录输入和人的预期，模型只建议。模型检查点、预处理表示、候选定义和评分器须作为一组指定并校验；不能把 R21 的原始输入格式与 R27 的数值关系格式互换。权重传输或访问 Spark 评分需要单独连接，没有已发布的模型 HTTP 服务可假定存在。
5. **再决定是否接自动执行。** 真实偏好覆盖、错误分析、状态与权限门槛、人工恢复和业务验收完成后另行决定。现阶段不开无人值守自动控制。

第 1、2 步不依赖决策模型先训练完。办公室可以先验证“我明确要求操作这盏灯 → 正确执行并读回”；这与“模型自行判断何时开灯”是两个验收问题。
